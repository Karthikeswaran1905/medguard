# MedGuard — Setup

This is a working Flutter + Firebase implementation of the MedGuard MVP
(Section 32 of `docs/MedGuard_Complete_Report_Flutter_Supabase.pdf`), wired
to the v2 architecture in Part II of that report: multi-tenant schema,
invite-code Doctor–Patient linking, the full escalation chain, and
timezone-aware scheduling via Cloud Functions.

**This project originally shipped on Supabase/Postgres.** It has since been
migrated to Firebase (Auth + Firestore + Cloud Functions + Cloud
Scheduler) — every table became a Firestore collection, every RLS policy
became a Firestore Security Rules statement, and every Edge Function
became a Cloud Function. The mapping is documented inline throughout
`firestore.rules` and `functions/src/*.ts`.

## Running on the Spark (free) plan

Firebase Authentication and Firestore (Native mode) are free on Spark with
generous daily quotas — sign-in/sign-up, every dashboard, and Firestore
reads/writes/queries all work today with **no Blaze upgrade and no
`firebase deploy` at all**. Two things on Firebase's side specifically
need Blaze (pay-as-you-go — it still has its own no-cost usage tier for
light traffic, it just requires a linked billing account) and don't work
on Spark no matter what:

- **Cloud Functions** — can't be deployed on Spark, full stop (`firebase
  deploy --only functions` fails outright). This is what
  `createStaffUser`, `linkPatient`, `scheduleGenerator`,
  `escalationEngine`, `sendNotification` and `aiInsightsBatch` all are.
  - `createStaffUser` — **worked around**: `PeopleRepository
    .createStaffAccount` (Add doctor/incharge/caretaker) now creates the
    account entirely client-side instead of calling this function — see
    that method's doc comment. Nothing to deploy for this one anymore.
  - `linkPatient`, `scheduleGenerator`, `escalationEngine`,
    `sendNotification`, `aiInsightsBatch` — **still Blaze-only, not yet
    worked around.** Concretely, on Spark: a patient signing up *with* an
    invite code will get an error at the `linkPatient` call (signing up
    *without* a code still works — they're just created unlinked, same as
    today); no `medication_events` ever get created since nothing
    generates them (`scheduleGenerator`), so Today's Schedule / dose
    reminders stay empty even after a Doctor prescribes something;
    nothing escalates a missed dose (`escalationEngine`) or pushes a
    notification (`sendNotification`); and the nightly AI insight batch
    never runs. These would each need Blaze, or a client-side rework
    (harder for these five than it was for staff creation — `scheduleGenerator`
    and `escalationEngine` are "every minute" background jobs with no
    clean client-only equivalent). Ask if you'd like any of these tackled
    next.
- **Cloud Storage for Firebase** — as of a September 2024 policy change,
  provisioning or accessing *any* Cloud Storage bucket (even the free
  usage tier) now requires Blaze too; Spark projects get a 402/403 error.
  That's what the Health Record Vault and the Prescription Scanner's image
  upload both write to (`storage.rules`, `firebase_storage` package) — so
  both will fail to upload on Spark specifically at that step, even though
  everything else on their screens (the UI, the Firestore-backed review/
  confirm flow) works.

If light usage is all you need, Blaze's own free tier usually covers a
project this size for Functions and Storage both — upgrading doesn't
necessarily mean a bill, just that the option to bill exists. That's the
straightforward way to unlock everything above; a Spark-only rework of
`scheduleGenerator`/`escalationEngine` specifically is possible but a much
bigger change than what shipped so far.

## What's implemented vs. stubbed

Implemented and working once Firebase is deployed (step 2):

- Firebase Auth sign-in/sign-up; role-based routing to five dashboards.
- Patient self-registration with optional Doctor invite code (Section 39).
- Doctor: prescribe medicines with dose/times/duration, add Incharges,
  generate invite codes, allocate an Incharge to a patient.
- Incharge: add Caretakers, allocate a Caretaker to a patient, view
  patients/adherence/escalated-alert counts.
- Caretaker: see assigned patients, verify pending medication events.
- Admin/Dean: add Doctors, org-wide counts.
- Full v2 Firestore data model and Security Rules (`firestore.rules`,
  `firestore.indexes.json`).
- Cloud Functions for staff-account creation, invite-code linking,
  timezone-aware schedule generation, the three-level escalation engine,
  push-notification dispatch, and nightly AI insight generation
  (`functions/src/`).
- **Device push token registration** (Section 43) — `NotificationsRepository`
  requests notification permission and registers/refreshes this device's
  FCM token in `device_tokens` as soon as a profile is known
  (`AuthGate`), and unregisters it on sign-out (`RoleScaffold`'s sign-out
  button) so a token never outlives the session it was created for. See
  "Enabling push on iOS" below for the two steps this can't do by itself.
- **AI insights dashboard** (Section 44) — Doctor, Incharge and Caretaker
  dashboards each show an "AI insights" section listing every patient they
  can see who has a recent `aiInsightsBatch` result
  (`AnalyticsRepository.latestInsightsForPatients` + the shared
  `InsightTile` widget). Admin/Dean and Patient don't get this section —
  Admin works at the org level and a patient's own insight isn't
  currently surfaced to them, only to whoever is monitoring them.
- **MedGuardian AI UI features** — the UI plan from
  `docs/MedGuardian_AI_Clean_Architecture_Working_Flow_UI_Features.pdf`,
  built on top of the existing data model rather than replacing it. Every
  screen below is fully navigable and, except where noted, fully working
  end-to-end today:
  - **Prescription Scanner + OCR Review** (`features/prescriptions/`) —
    capture/upload a prescription photo, then review/edit the details by
    hand and confirm. **The upload step needs Blaze** — it writes to
    Firebase Storage, which requires Blaze regardless of file size or
    volume (see "Running on the Spark plan" above); everything else on
    this screen works on Spark. **OCR/Gemini extraction itself is
    stubbed** — the
    fields start blank instead of pre-filled — this is the deferred "API"
    work. Confirming saves a `prescription_scans` draft rather than a live
    prescription: only a linked Doctor can create real `medicines`/
    `medication_schedules` documents (Firestore Security Rules), so a
    patient's scan shows up on their Doctor's dashboard
    ("Scanned prescriptions") as something to act on, instead of silently
    bypassing that safety boundary. See the doc comment on
    `PrescriptionScan` for the full reasoning.
  - **AI Assistant** (`features/ai/ai_assistant_screen.dart`) — a chat UI
    backed by `AiAssistantRepository`, currently a local FAQ over common,
    safe medication questions. Real Gemini wiring is a single-method
    change (`AiAssistantRepository.ask`) once the API work resumes — see
    that file's doc comment.
  - **Health Record Vault** (`features/health_records/`) — fully real:
    uploads go to Firebase Storage with Firestore metadata
    (`health_records`), no AI/OCR dependency. Patient can upload/view/
    delete their own; Doctor/Incharge/Caretaker get a read-only view from
    a patient's card. **The upload itself needs Blaze**, same as the
    Prescription Scanner above — the screen, the metadata list, and
    deleting an existing record all work on Spark; only the file upload to
    Storage doesn't.
  - **Drug Interaction Checker** (`features/interactions/`) — fully real,
    local rule-based check (`DrugInteractionChecker`) over a small,
    well-known set of interacting medicine pairs, run against the
    patient's active medicines. Explicitly labeled reference-only, not
    exhaustive, not a substitute for a pharmacist/doctor.
  - **Emergency QR Health Card** (`features/emergency_qr/`) — fully real,
    fully offline: generates a QR code from the patient's own blood
    type/allergies/conditions (stored on their existing `patients/{uid}`
    document) plus their emergency-marked family contacts. No new backend
    needed.
  - **Alert detail** (`features/caretaker/alert_detail_screen.dart`) —
    patient / medicine / scheduled time / status / a 7-day repeated-miss
    count / emergency contacts, reused from the Caretaker's pending list
    (with the verify action) and the Incharge's new tappable "Escalated"
    stat tile (read-only list of every escalated, still-open event across
    their patients).
  - **Patient role UI** (`features/patient/`) — redesigned to match the
    six-screen mockup set (Home / Medications / AI Insights / Records /
    Profile), replacing the old single-screen dashboard with a Material 3
    bottom-nav shell (`PatientShell`, `IndexedStack` so each tab keeps its
    state):
    - **Home** (`patient_home_screen.dart`) — greeting header, a real
      notification-bell badge (today's pending-dose count, not a placeholder),
      an "Adherence Today" gradient card with a progress ring, a "Next Dose"
      action card (or an all-caught-up state), and a preview of today's
      schedule.
    - **Today's Schedule** (`today_schedule_screen.dart`) — a Sun–Sat day
      picker over `MedicationRepository.fetchEventsForDate`, with
      Mark-as-Taken / Mark-as-Missed on pending doses (`markMissed` is new).
    - **Medications** (`medications_list_screen.dart`,
      `medication_details_screen.dart`) — active/past medicine list plus a
      details screen (dose/frequency/time/duration/prescribed-by, the last
      two resolved via the new `fetchSchedulesForMedicine`/
      `fetchPrescription`/`fetchProfile` repository methods) and an "About
      this medicine" reference blurb (`lib/data/medicine_info.dart` — small
      static, substring-matched dataset, same non-exhaustive/reference-only
      pattern as the Drug Interaction Checker). **Edit/Delete are shown for
      visual parity with the mockup but open an explanatory dialog instead
      of writing** — Firestore Security Rules give a patient no
      `update`/`delete` permission on `medicines`; only the prescribing
      Doctor can change it.
    - **AI Insights** (`ai_insights_screen.dart`) — Overview/Trends tabs
      over `MedicationRepository.fetchHistory`: a 7-day adherence bar
      chart, the same `AnalyticsRepository` AI insight card Doctor/Incharge/
      Caretaker see, a missed-doses summary, and a 4-week trend view. No new
      backend — reuses existing repositories.
    - **Records** and **Profile** — `HealthRecordsScreen` gained a
      `showChrome` flag so the same screen serves as both a standalone
      pushed screen (Doctor/Caretaker/Incharge) and bare tab content here;
      `profile_screen.dart` is new, with quick links to AI Assistant, Drug
      Interaction Checker, Emergency QR, and scanned prescriptions, plus
      sign out.
    - The **Add Prescription** (prescription scanner) and **AI Extracted
      Medicines** (OCR review) screens were restyled to match the mockup
      (dashed-border scan card, single numbered medicine card) without
      changing their underlying behavior or the OCR-is-stubbed disclosure.

Stubbed / left for the next iteration (called out explicitly rather than
silently skipped):

- **Offline-first sync** (Section 42) — `medication_events` documents have
  `serverReceivedAt` / a place for sync status, but the Flutter app doesn't
  yet queue confirmations locally when offline. (Firestore's own offline
  persistence cache is a natural fit here if you want to build this out —
  more so than the original Postgres version had available.)
- **Unlinked-patient review queue** (Section 39) — a patient who signs up
  without an invite code is created with no `doctor_patient_links`
  document at all, and nothing surfaces them to a Doctor/Admin for manual
  linking yet.
- **`audit-writer`** from the Section 48 catalog was folded into each Cloud
  Function writing its own `audit_logs` document directly, rather than
  shipped as a separate function — simpler for a reference implementation.
- The caretaker's `medication_events` update rule allows setting
  `finalStatus` directly, matching `MedicationRepository.verifyEvent`.
  Section 46 recommends this become Cloud-Function-only once
  `escalationEngine` is the sole writer of `finalStatus` in production.
- **Resolved, not stubbed**: staff-invite emailing used to be listed here
  as a gap (the old `createStaffUser` Cloud Function generated a
  password-reset link via the Admin SDK but didn't email it). Since
  account creation moved client-side for the Spark plan (see "Running on
  the Spark plan" above), it calls `sendPasswordResetEmail` instead, which
  *does* email the new person directly through Firebase Auth's own
  template — nothing left to relay by hand.

## 1. Prerequisites

```bash
npm install -g firebase-tools   # if you don't already have it
firebase login
```

Confirm the CLI is pointed at the right project:

```bash
firebase use medguard-10105
```

## 2. Deploy Firestore rules and indexes (Spark-compatible)

```bash
flutter pub get
firebase deploy --only firestore:rules,firestore:indexes
```

`flutter pub get` picks up the three packages this build added
(`firebase_storage`, `image_picker`, `qr_flutter`) — see "MedGuardian AI UI
features" above. (`firebase_storage` is still a dependency so the code
compiles even though the Storage *backend* itself needs Blaze — see below.)

This deploys, on Spark, with no billing account needed:
- `firestore.rules` — every collection's read/write rules (Section 46's
  RLS policies, translated), including `prescription_scans`,
  `health_records`, and `canCreateStaffRole()` for client-side staff
  creation (see "Running on the Spark plan" above).
- `firestore.indexes.json` — the composite indexes the repository queries
  need (equality + range/orderBy combinations Firestore can't serve
  without one).

### 2b. Once you're on Blaze: Storage rules and the remaining Cloud Functions

```bash
cd functions
npm install
cd ..
firebase deploy --only storage,functions
```

- `storage.rules` — Firebase Storage rules for `prescription_scans/` and
  `health_records/` (the Prescription Scanner and Health Record Vault
  images/documents). Needs Blaze as of Cloud Storage for Firebase's
  September 2024 billing change — there's no Spark-plan path for this one.
- The 5 functions in `functions/src/` that still matter on this build:
  `linkPatient` (callable, invoked from the Flutter app via
  `cloud_functions`), `scheduleGenerator` / `escalationEngine` /
  `aiInsightsBatch` (all `onSchedule` — Firebase provisions their Cloud
  Scheduler jobs automatically on deploy, no separate cron step needed),
  and `sendNotification` (exposed both as a plain internal function that
  `escalationEngine` calls directly, and as its own callable). A 6th,
  `createStaffUser`, is still exported for parity but the app no longer
  calls it — Add doctor/incharge/caretaker works today without this
  deploy step at all (see above).

Set the AI provider secret before `aiInsightsBatch` will produce real
insights instead of a placeholder string:

```bash
firebase functions:secrets:set AI_API_KEY
```

(You'll be prompted to paste the key — it isn't stored in your shell
history or in any file in this repo.)

## 3. Firestore composite indexes

If you skip `firestore:indexes` in the deploy command above, the first
time each affected query runs Firestore returns an error containing a
direct link to create that specific index — click it, or just run
`firebase deploy --only firestore:indexes` once up front to create all of
them from `firestore.indexes.json` at once.

## 4. Bootstrap the first Admin/Dean account

Every other account is created top-down by `PeopleRepository
.createStaffAccount` (Admin adds a Doctor, who adds an Incharge, who adds
a Caretaker), so the very first Admin has to be seeded directly. Create
the Auth user from the
Firebase Console (Authentication → Add user), then add their Firestore
documents — easiest from the Firebase Console's Firestore tab, or with a
short one-off Admin SDK script:

```js
// functions/scripts/seedAdmin.js (run once with `node seedAdmin.js` after
// `npm install firebase-admin` and pointing GOOGLE_APPLICATION_CREDENTIALS
// at a service account key, or via `firebase functions:shell`)
const admin = require("firebase-admin");
admin.initializeApp();
const db = admin.firestore();

(async () => {
  const orgRef = db.collection("organizations").doc();
  await orgRef.set({ name: "Example Institution", type: "college", createdAt: new Date() });

  const adminUid = "<the auth user id you just created>";
  await db.collection("profiles").doc(adminUid).set({
    orgId: orgRef.id,
    role: "admin",
    fullName: "Dean Name",
    email: "dean@example.edu",
    timezone: "Asia/Kolkata",
    createdAt: new Date(),
  });
  console.log("Seeded org", orgRef.id, "and admin", adminUid);
})();
```

## 5. Run the Flutter app

`firebase_options.dart` already has the project's config baked in (via
`flutterfire configure`), so no `--dart-define` flags are needed for
Firebase itself:

```bash
flutter pub get

```

## 6. Enabling push on Android

Android needs nothing further — `google-services.json` (already generated
by `flutterfire configure`) plus the `POST_NOTIFICATIONS` permission and
default notification channel already added to `AndroidManifest.xml` are
enough for `NotificationsRepository` to register a token and for
`sendNotification` to deliver to it.

## 7. Enabling push on iOS

Two steps here need Xcode/the Firebase Console directly — neither is a
plain text file this session could safely hand-edit, so they're still
yours to do:

1. In Xcode, open `ios/Runner.xcworkspace`, select the Runner target →
   Signing & Capabilities → **+ Capability** → add **Push Notifications**
   (this creates `Runner.entitlements` and wires it into the build
   automatically).
2. Generate an APNs authentication key in the Apple Developer portal
   (Certificates, Identifiers & Profiles → Keys), then upload it in the
   Firebase Console under Project Settings → Cloud Messaging → Apple app
   configuration.

`Info.plist` already has the `remote-notification` background mode added
so the app can process a push once these two are done.
